# Платформа цифрового двійника

## Перевірка API

Стенд запущено командою `docker compose up -d` у каталозі `platform/`. Служби Ditto перейшли в стан `healthy`, перевірка стану платформи повертає `UP`:

```
$ curl http://localhost:8080/health
{"status":"UP"}
```

**1. Створення тестового двійника.** Запит `PUT` створює двійник із заданим ідентифікатором або замінює наявний.

```
$ curl -i -u ditto:ditto -X PUT -H "Content-Type: application/json" \
  -d '{"attributes": {"purpose": "перевірка"}}' \
  http://localhost:8080/api/2/things/org.pzks:test-1
HTTP/1.1 201 Created
Location: http://localhost:8080/api/2/things/org.pzks:test-1
ditto-originator: nginx:ditto
entity-revision: 1
etag: "rev:1"

{"thingId":"org.pzks:test-1","policyId":"org.pzks:test-1","attributes":{"purpose":"?????????"}}
```

Код `201 Created` підтверджує, що двійник створено. Заголовок `entity-revision: 1` — номер ревізії: кожна зміна двійника збільшує його на 1 (на цьому ґрунтується перевірка пропущених оновлень на занятті 4). `ditto-originator` показує, від чийого імені виконано запит.

*Примітка.* Замість слова «перевірка» збереглися знаки питання: у Git Bash на Windows кирилиця в аргументі командного рядка передається в `curl` не в кодуванні UTF-8. Для справжніх двійників станції дані надсилаються з файлів (`--data @файл`), де кодування UTF-8 зберігається.

**2. Читання двійника.**

```
$ curl -u ditto:ditto http://localhost:8080/api/2/things/org.pzks:test-1
{"thingId":"org.pzks:test-1","policyId":"org.pzks:test-1","attributes":{"purpose":"?????????"}}
```

Двійник містить ідентифікатор `thingId`, посилання на політику доступу `policyId` і атрибут, заданий під час створення.

**3. Читання політики доступу.**

```
$ curl -u ditto:ditto http://localhost:8080/api/2/policies/org.pzks:test-1
{"policyId":"org.pzks:test-1","imports":{},
 "entries":{"DEFAULT":{
   "subjects":{"nginx:ditto":{"type":"generated"}},
   "resources":{
     "thing:/":{"grant":["READ","WRITE"],"revoke":[]},
     "policy:/":{"grant":["READ","WRITE"],"revoke":[]},
     "message:/":{"grant":["READ","WRITE"],"revoke":[]}},
   "importable":"implicit"}}}
```

Політику не задавали явно, тому Ditto створив її автоматично з тим самим ідентифікатором і одним записом `DEFAULT`: суб’єкт `nginx:ditto` (користувач, від імені якого виконано запит) отримав права `READ` і `WRITE` на сам двійник (`thing:/`), на його політику (`policy:/`) і на повідомлення (`message:/`). Для двійника станції на кроці 7 політику буде задано явно, з окремим обмеженим записом для з’єднання телеметрії.

Також перевірено вебконсоль Ditto (http://localhost:8080/ui/) та опис API (http://localhost:8080/apidoc/).

## Структура двійника

Станцію описано **одним двійником** `org.pzks:station-1`. Склад двійника — чотири функціональні блоки (features): `station` (вузли станції), `pump1` і `pump2` (насоси Н1 і Н2, обидва одного типу) та службовий `sync`. Елементи поділено на чотири види з табл. 1 методички.

| Елемент | Вид | Ditto | Джерело |
|---|---|---|---|
| Назва станції | паспорт | `attributes/name` | паспорт станції |
| Адреса станції | паспорт | `attributes/address` | паспорт станції |
| Номінальний тиск на виході | паспорт | `attributes/ratedOutletPressure` | проєкт станції |
| Модель насосів | паспорт | `attributes/pumpModel` | паспорт насоса |
| Заводські номери Н1 і Н2 | паспорт | `attributes/pump1SerialNo`, `attributes/pump2SerialNo` | паспорт насоса |
| Квартал, який обслуговує станція | зв’язок `serves` | `attributes/district` (thingId `org.pzks:district-1`) | проєкт станції |
| Тиск на вході | стан | `features/station/properties/inletPressure` | S-03 |
| Тиск на виході | стан | `features/station/properties/outletPressure` | S-04 |
| Витрата води | стан | `features/station/properties/flow` | S-05 |
| Сухий хід | стан | `features/station/properties/dryRun` | S-14 |
| Режим станції | стан | `features/station/properties/mode` | S-15 |
| Фактична уставка тиску | стан | `features/station/properties/setpoint` | S-16 |
| Вібрація (СКЗ) Н1 / Н2 | стан | `features/pump1/properties/vibration`, `features/pump2/…` | S-01, S-02 |
| Частота обертання Н1 / Н2 | стан | `features/pump1/properties/speed`, `features/pump2/…` | S-06, S-07 |
| Електрична потужність Н1 / Н2 | стан | `features/pump1/properties/power`, `features/pump2/…` | S-08, S-09 |
| Температура підшипника Н1 / Н2 | стан | `features/pump1/properties/bearingTemperature`, `features/pump2/…` | S-10, S-11 |
| Стан насоса Н1 / Н2 | стан | `features/pump1/properties/state`, `features/pump2/…` | S-12, S-13 |
| Номер повідомлення, час відліку | стан (службовий) | `features/sync/properties/seq`, `ts` | шлюз станції |
| Змінити уставку тиску | функція | повідомлення inbox `set-setpoint` | оператор (FR-08) |
| Пустити / зупинити насос | функція | повідомлення inbox `start-pump`, `stop-pump` | оператор (FR-08) |
| Перемкнути режим | функція | повідомлення inbox `set-mode` | оператор (FR-08) |
| Квитувати тривогу | функція | повідомлення inbox `acknowledge-alarm` | оператор (FR-06) |

**Як виражено зв’язки.** У Ditto немає окремої сутності «зв’язок», тому використано два способи:
- **зв’язок з іншим двійником** (станція *обслуговує* квартал) зберігається як атрибут `district` з ідентифікатором іншого двійника. Ditto бачить у ньому лише рядок, а що саме означає цей зв’язок, фіксує онтологія (заняття 2, властивість `serves`);
- **склад** (станція *має частину* насос) виражено функціональними блоками `pump1` і `pump2` всередині одного двійника. В онтології це зв’язок `hasPart`.

**Паспорт і стан** розділено так, як вимагає вісь «тип — екземпляр»: паспортні дані змінюються рідко й зберігаються в атрибутах, а значення сигналів оновлюються телеметрією у функціональних блоках.

## Порівняння платформ

Порівнюємо Eclipse Ditto з двома альтернативами: керованим хмарним сервісом **Azure Digital Twins** і відкритою платформою **Eclipse BaSyx** (реалізація оболонки керування активом AAS). Зведена оцінка — за формулою `S = Σ wᵢ·sᵢ / Σ wᵢ`, оцінки `sᵢ` — у шкалі 1–5.

### Ваги критеріїв (задано до оцінювання платформ)

Ваги випливають з вимог і архітектури ЛР 1, а не з властивостей платформ:

| Критерій | w | Чому така вага |
|---|---:|---|
| Відкритість (ліцензія, формат моделі) | 0,20 | водоканал не повинен залежати від одного постачальника; модель має бути в стандартному форматі |
| Локальне розгортання | 0,20 | станція — критична інфраструктура, платформа працює в ЦОД водоканалу (подання розгортання ЛР 1) |
| Підтримка протоколів | 0,20 | телеметрія йде через MQTT (ЛР 1), платформа має приймати її без проміжних сервісів |
| Масштабованість | 0,15 | NFR-03 вимагає лише 10 станцій (≈ 272 повідомлення/с), це невелике навантаження |
| Вартість володіння | 0,15 | бюджет комунального підприємства обмежений |
| Зрілість спільноти | 0,10 | важлива для підтримки, але не визначальна |
| **Разом** | **1,00** | |

### Оцінки

| Критерій | w | Ditto | Azure DT | BaSyx |
|---|---:|---:|---:|---:|
| Відкритість | 0,20 | 5 | 3 | 5 |
| Локальне розгортання | 0,20 | 5 | 1 | 5 |
| Підтримка протоколів | 0,20 | 5 | 2 | 3 |
| Масштабованість | 0,15 | 4 | 5 | 3 |
| Вартість володіння | 0,15 | 4 | 3 | 4 |
| Зрілість спільноти | 0,10 | 3 | 4 | 3 |
| **S за формулою (1)** | | **4,50** | **2,80** | **3,95** |

### Обґрунтування оцінок

**Eclipse Ditto**
- *Відкритість — 5:* відкритий код під ліцензією EPL-2.0; модель двійника — стандарт W3C WoT Thing Model ([інтеграція WoT](https://eclipse.dev/ditto/basic-wot-integration.html)).
- *Локальне розгортання — 5:* запускається з Docker Compose чи Helm на власному обладнанні — це й зроблено на стенді.
- *Протоколи — 5:* вбудовані з’єднання MQTT 3.1.1 і 5, AMQP, Kafka, HTTP з власним відображенням формату мовою JavaScript ([з’єднання](https://eclipse.dev/ditto/basic-connections.html), [огляд connectivity](https://eclipse.dev/ditto/connectivity-overview.html)).
- *Масштабованість — 4:* служби розгортаються кластером і розподіляють двійники між вузлами ([архітектура](https://eclipse.dev/ditto/architecture-overview.html)); оновлення одного двійника обробляються послідовно.
- *Вартість — 4:* ліцензія безкоштовна, але власну інфраструктуру треба підтримувати: стенд — 13 контейнерів і 4–6 ГБ пам’яті.
- *Спільнота — 3:* активний проєкт Eclipse Foundation, але спільнота менша, ніж у хмарних постачальників.

**Azure Digital Twins**
- *Відкритість — 3:* мова моделей DTDL відкрита ([DTDL v3](https://learn.microsoft.com/en-us/azure/digital-twins/concepts-models)), але сам сервіс закритий і доступний лише в Azure.
- *Локальне розгортання — 1:* це хмарна послуга PaaS, розгорнути її в ЦОД водоканалу неможливо.
- *Протоколи — 2:* сервіс не приймає MQTT від пристроїв напряму; телеметрію доставляють через Azure IoT Hub і функцію Azure Functions ([приймання телеметрії](https://learn.microsoft.com/en-us/azure/digital-twins/how-to-ingest-iot-hub-data)).
- *Масштабованість — 5:* керований сервіс, масштабування — відповідальність Microsoft ([обмеження сервісу](https://learn.microsoft.com/en-us/azure/digital-twins/reference-service-limits)).
- *Вартість — 3:* немає витрат на власне обладнання, але оплата залежить від кількості операцій, повідомлень і запитів ([ціни](https://azure.microsoft.com/en-us/pricing/details/digital-twins/)); за безперервної телеметрії сума росте з кожною станцією.
- *Спільнота — 4:* велика екосистема й документація Microsoft.

**Eclipse BaSyx**
- *Відкритість — 5:* відкритий код під ліцензією MIT; модель — стандартна оболонка керування активом AAS ([репозиторій](https://github.com/eclipse-basyx/basyx-java-server-sdk)).
- *Локальне розгортання — 5:* готові образи Docker для всіх компонентів.
- *Протоколи — 3:* компоненти надають REST API за специфікацією AAS і події MQTT, але приймання телеметрії від пристроїв потребує окремого компонента-мосту, а не вбудованого з’єднання з відображенням.
- *Масштабованість — 3:* компоненти можна дублювати з базою MongoDB, але досвіду великих розгортань менше.
- *Вартість — 4:* безкоштовна, витрати — на власну інфраструктуру.
- *Спільнота — 3:* активна, переважно в німецькій промисловій екосистемі Industrie 4.0.

### Висновок

Найвищу оцінку отримала **Eclipse Ditto (S = 4,50)**. Вирішальними стали три критерії з найбільшою вагою: відкритість, локальне розгортання й вбудована підтримка MQTT. Azure Digital Twins виграє лише за масштабованістю й спільнотою, але не розгортається локально. BaSyx близька до Ditto за відкритістю й розгортанням, але програє в прийманні телеметрії. Рішення оформлено в `docs/adr/0004-vybir-platformy.md`.

**Перевірка на підгонку ваг** (методичка): ваги задано з вимог ЛР 1 до оцінювання. Навіть якби всі шість критеріїв мали однакову вагу, порядок не змінився б: Ditto — 4,33, BaSyx — 3,83, Azure DT — 3,00.
