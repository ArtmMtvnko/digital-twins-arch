# ADR-0005. Синхронізація спільної 3D-сцени: авторитетний сервер сеансу зі знімками й інтерполяцією

## Статус

Прийнято, 2026-11-23

## Контекст

- Кілька учасників (диспетчер, інженер, віддалений експерт) разом оглядають 3D-сцену станції: бачать аватари одне одного й ставлять позначки на обладнанні (`docs/multiuser.md`).
- Спільний віртуальний стан має дві різні за природою частини: **пози аватарів** змінюються безперервно (20 разів за секунду), і кожна наступна замінює попередню; **позначки** змінюються подіями, і жодну зміну не можна втратити.
- Фізичний стан станції вже має джерело істини — платформу Eclipse Ditto (ADR-0004); кожен клієнт отримує його сам.
- Учасники можуть працювати з різних мереж. Виміряно для трьох модельних профілів (`results/net-*.json`): затримка показу іншого учасника з інтерполяцією — 100 / 164 / 208 мс (медіана) для локальної, міської й мобільної мережі; з екстраполяцією за мобільної мережі — 74 мс, але з відхиленням до 13 см на різких зупинках.
- Вихідний потік сервера росте як O(N²): 121 кбіт/с для 3 учасників, ≈ 1,5 Мбіт/с для 10.

## Варіанти

1. **Однорангова мережа (WebRTC, кожен з кожним)** — без сервера, найменша затримка, але кожен клієнт надсилає позу N − 1 учасникам, немає джерела істини для позначок (хто вирішує, чия позначка правильна), потрібні сервер сигналізації та TURN для обходу NAT.
2. **Авторитетний сервер сеансу, WebSocket, знімки 20 Гц, інтерполяція на клієнті** — сервер перевіряє кожне введення й тримає позначки, клієнти показують інших у момент t − D_інт.
3. **Те саме, але екстраполяція** замість інтерполяції — затримка менша майже втричі (74 мс замість 208 мс за мобільної мережі), але аватар проскакує вперед на різких зупинках (виміряно 12,9 см).
4. **Сервер з двома каналами:** пози — невпорядкованим ненадійним каналом WebRTC, позначки — WebSocket — найкраще за втрат, але значно складніше (сигналізація, TURN, два канали).

## Рішення

Обрано **варіант 2**:
- **сервер сеансу авторитетний** для віртуального стану: приймає пози, перевіряє межі території, нумерує й зберігає позначки (видаляти — лише автору), кожному новому учасникові надсилає повний перелік позначок;
- **WebSocket** для поз і позначок, **знімки стану 20 разів за секунду** (T_зн = 50 мс);
- **інтерполяція на клієнті** з D_інт за виразом (5) і **m = 1 для всіх профілів**: прогін у локальній мережі з m = 0 показав 35,5 % кадрів без новішого знімка, бо фактичний розкид надходження знімків (≈ 15 мс) більший за номінальний джитер. На навчальному стенді профілі в `scene/shared.js` залишено як у методичці (для lan m = 0), щоб виміри були відтворюваними; m = 1 — рішення для продуктивного розгортання, про це є коментар у коді;
- **стан двійника сервер сеансу не пересилає**, і **жодних команд фізичному об’єкту** цим каналом.

## Наслідки

- **+** Позначки мають одне джерело істини: усі учасники бачать той самий перелік, а суперечливі зміни розв’язує сервер.
- **+** Аватари рухаються плавно й точно на траєкторії (відхилення до 2 мм) у всіх трьох профілях мережі.
- **+** Один простий канал WebSocket замість сигналізації WebRTC і TURN.
- **−** Інтерполяція додає затримку: за мобільної мережі інших учасників видно із запізненням ≈ 0,2 с — досить для спільного огляду, але не для щільно скоординованих дій.
- **−** Через TCP втрачений сегмент затримує й наступні пози (за 2 % втрат — на один RTT); за гіршої мережі варто перейти до варіанта 4.
- **−** Потік сервера росте як O(N²): понад ≈ 10 учасників знадобиться керування зацікавленістю.
- **−** Сервер — єдина точка відмови віртуального стану: позначки зберігаються лише в пам’яті й зникнуть після його зупинки (3D-подання стану двійника при цьому працює).
