# Відповідність еталонній моделі ISO 23247

ISO 23247 написано для виробництва, тому спершу пояснюємо, що означає кожна категорія стандарту для насосної станції (таблиця 1). Потім зіставляємо складники нашої платформи із сутностями стандарту (таблиця 2) і рахуємо покриття.

## Таблиця 1. Склад об’єкта за категоріями OME

OME (observable manufacturing elements) — спостережувані елементи, тобто сам фізичний об’єкт.

| Категорія OME | Що з нашої станції сюди належить | Як потрапляє у двійник |
|---|---|---|
| Обладнання | насоси Н1 і Н2 з двигунами, частотні перетворювачі, датчики, шафа керування з ПЛК | сигнали S-01 – S-13: вібрація, температура, оберти, потужність, стан насосів |
| Персонал | черговий оператор на місці, ремонтна бригада | датчиками не відстежується; присутність видно опосередковано — через перемикання в сервісний режим (S-15) і через журнал квитування тривог |
| Матеріали | вода з міської магістралі на вході станції | S-03 (тиск на вході), S-14 (сухий хід — води на вході немає) |
| Процес | підвищення тиску, регулювання обертів, режими роботи | S-04 (тиск на виході), S-15 (режим), S-16 (фактична уставка) |
| Приміщення | будівля станції | **порожня**: температура в приміщенні й затоплення не вимірюються (свідоме обмеження — див. нижче) |
| Довкілля | погода, сезон, час доби | **порожня**: окремо не вимірюється; вплив на споживання видно опосередковано через витрату (S-05) |
| Продукт | вода під тиском ≈ 5 бар, що йде в мережу кварталу | S-04 (тиск на виході), S-05 (витрата) |
| Документація | паспорти насосів (номінальні параметри, допустима вібрація), журнал ремонтів | не сигнали, а статичні дані двійника: паспорт зберігається як властивості типу насоса, журнал ремонтів — як історія примірника |

## Таблиця 2. Відповідність сутностям ISO 23247

| Сутність ISO 23247 | Складник платформи | Блок SysML | Статус |
|---|---|---|---|
| DCE: збирання даних | шлюз станції (опитує ПЛК, рахує СКЗ вібрації, ставить мітки часу, буферизує дані) + MQTT-брокер | `StationGateway`, `MqttBroker` | закрито |
| DCE: керування пристроями | шлюз станції записує уставки й команди в ПЛК; диспетчер команд у сервісі синхронізації | `StationGateway`, `SyncService` | закрито |
| DTE: застосунки та служби | сервіс аналітики (енергоефективність, аномалії, тривоги); 3D-сцена у веб-застосунку | `AnalyticsService`, `WebApp` | закрито |
| DTE: доступ до ресурсів та обмін | API сервісу стану двійника (Eclipse Ditto); сховище часових рядів (TimescaleDB) | `TwinStateService`, `HistoryStore` | закрито |
| DTE: функціонування та керування | сервіс синхронізації: оновлення reported / desired, позначка «застарілий»; модель двійника в Ditto | `SyncService`, `TwinStateService` | закрито |
| UE: користувач | веб-застосунок для оператора та інженера | `WebApp` | закрито |
| Наскрізна: захищеність | TLS, логін і пароль, ролі, журнал команд | `SecurityServices` | закрито |
| Наскрізна: якість даних | перевірка повідомлень (дублікати, діапазон); позначка застарілих даних; синхронізація годинників через NTP | `SyncService` (валідатор) | закрито |
| Наскрізна: взаємодійність | стандартні протоколи на кожній ділянці: OPC UA / Modbus до ПЛК, MQTT для телеметрії, HTTP / SSE для API | порти й інтерфейси блоків | закрито |

## Покриття еталонної моделі

Усі 9 сутностей застосовні до нашого об’єкта, і для кожної є відповідник:

```
C = n_відп / n_етал · 100 % = 9 / 9 · 100 % = 100 %
```

Незастосовних і незакритих сутностей немає. Але 100 % означає лише те, що для кожної сутності є **хоча б один** відповідник. Три сутності закриті не повністю, і це свідомі обмеження ЛР 1:

| Сутність | Що не охоплено | Чому |
|---|---|---|
| UE: користувач | суміжні системи водоканалу (SCADA, планування ремонтів) не підключені | платформа поки працює з однією станцією; інтеграцію варто додати, коли станцій стане кілька |
| Наскрізна: взаємодійність | немає стандартної інформаційної моделі насоса (наприклад, оболонки керування активом AAS), модель двійника описана власним форматом JSON у Ditto | для однієї станції власна модель простіша; перехід на AAS потрібен для обміну з постачальниками обладнання |
| DTE: функціонування та керування | немає моніторингу стану самої платформи (чи працюють сервіси, чи не переповнене сховище) | на рівні ЛР 1 досить позначки «застарілий» стан; моніторинг платформи — кандидат для ЛР 2 |

Так само свідомо порожні дві категорії OME з таблиці 1:
- **приміщення** — датчики температури й затоплення в приміщенні станції можна додати пізніше без зміни архітектури: це лише нові сигнали в реєстрі;
- **довкілля** — погода впливає на споживання, але для керування станцією достатньо бачити саму витрату.
